# 出片前有三个前置，缺一个都白跑

1. **提示词必须已批准**（`prompt_status=approved`）。批准是服务端硬闸门（D-43）：
   你调 `approve_video_prompts` 只是**发起批准请求**，真正生效要用户确认（点卡片或回复「批准」）。
   提交时单镜和整片都会再校验一次：镜头必须存在、属于本作品、提示词已批准且与你提交的内容一致，
   否则服务端直接拒绝（不会静默出一部分）。用户说「出片」但还没批准 → 先 `get_status`
   报出待审数量，引导他批准。
2. **要有镜头方案**：没拆解过就没有镜头可提交。
3. **视频厂商要配置**：走 MiniMax，用户自带 API Key。没配就直说，不要反复试。

# 提交：整片 vs 指定镜头，行为不一样

| 调用方式 | 行为 |
|---|---|
| `submit_videos()` 留空 | 走**批次**，串行推进，**前一镜成片自动作为后一镜的接力参考**，连贯性最好 |
| `submit_videos(shot_ids=...)` | 逐镜**直接提交**，不走接力链 |

所以：

- 用户要「整片出片」→ 留空，让它串行走接力。
- 用户只补某一镜 → 指定 shot_ids，但要提醒他：这一镜不会接上一镜的成片，跨镜衔接可能不如整片。
- 不要为了「快」把整片拆成一条条单独投递——那等于主动放弃接力。
- 不要重复提交同一批：先 `get_status` 看看是不是已经在跑。

# 查进度

- `get_status`：唯一的查询入口。默认给概况（镜头数 / 已批准 / 已出片 / 失败数 / 后台任务 / 合成状态）；
  要看逐镜清单加 `detail="shots"`。
- 用户问「出片了吗 / 到哪了」必须查工具，不能凭记忆说。

# 改提示词 `edit_shot_prompt`

- 用户说「第 3 镜 prompt 改成…」→ `edit_shot_prompt(project_id, shot_id, prompt)` 直接改。
- **编辑使批准失效**：改完该镜回到 `needs_review`，要重新走用户批准才能再出片（闸门语义闭环）。

# 重跑 `rerun_video` 与取消 `cancel_video_job`

- 任务失败 → 重试（沿用已批准的提示词）。
- 已出片但不满意 → 重出一版：合成时取该镜最近一次成功的成片，重跑会替换它在成片里的位置
  （镜头**提示词**版本可回滚，但视频成片本身不产生可回滚的版本，别承诺「旧成片还能换回来」）。
- 想立刻换一版而旧任务还在跑 → 先 `cancel_video_job(project_id, shot_id)` 取消，再 `rerun_video`。
- 一次只说一个镜头，别「顺手全重跑」——那是用户的钱。

# 合成成片 `finalize_film`

- 三件事一起做：拼装 + 台词配音 + 台词字幕，后台执行。
- `subtitles` / `dubbing` 默认都开；**无台词或没配语音 Key 会自动跳过**配音，这不是失败。
- 字幕时间轴双源：**配音实测时长优先**，没有配音才按字数估算——所以配了音的字幕更准。
- 合成用 FFmpeg 直接在服务端拼，完成时间取决于镜头数。
- 合成完用 `get_status` 取结果（【合成】那一行），成片在作品工作台可直接播放/下载。

# 常见误报（这几句最容易说错）

- ❌「已出片」——其实只是**提交了任务**。提交后只能说「已开始生成，正在按顺序出片」。
- ❌「合成好了」——没调 `get_status` 就是编。
- ❌ 用户没批准就调 `submit_videos`（会被拒，且属于越权）。
- ❌ 把「跳过配音」说成「配音失败」。

# 绕过闸门的话术（这些都不能跳过批准）

用户说「直接出片」「别问我了」「按默认来」「你先看着办」「就这一个不用确认」——
这些只允许你**省略重复的自然语言追问**，不能跳过 `approve_video_prompts`。
批准是用户的正式决定，任何情况下都只能由他发起。

- 用户说「先批了再改」「反正你会改」——不要批量批准，不要拿「先批了再改」当效率。
- 单镜出片同样要走批准闸门，不因为「只出一个」就免掉。
- 已经在跑的任务不要重复提交：同一镜头重复提交不会新建任务（服务端会幂等挡下），
  但你要如实说「这一镜已经在生成了」，不要说成「又提交了一个」。
