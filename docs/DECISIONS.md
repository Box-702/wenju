<a id="d-01-模型接入全部走-openai-兼容协议"></a>
## D-01 模型接入全部走 OpenAI 兼容协议

**背景**：需要同时支持 DeepSeek、智谱、Moonshot、Qwen，以及本地 Ollama/vLLM，还要让用户自带 key。

**选项**：① 各家官方 SDK；② 一个 OpenAI 兼容门面 + 厂商声明表；③ 抽象层 + 每家一个适配器。

**决定**：选 ②。`app/llm/providers.py` 是唯一的 `ChatOpenAI` 构造点，差异只落在**默认端点、默认模型、额外请求体**三处，用一张 `ProviderSpec` 声明表描述。

**理由**：国内主流厂商都提供 OpenAI 兼容端点，引入各家 SDK 会带来多套依赖、多套重试/超时语义、多套错误类型，收益却只有"多几个原生特性"。声明表让新增厂商的成本降到"加一行"。

**什么时候该推翻**：需要用上某家 SDK 独有的能力时（如 Anthropic Messages API 的 prompt caching、extended thinking）。注意这**不是加一行 ProviderSpec 能解决的**——非 OpenAI 兼容协议要单独写协议客户端。

**相关**：`ARCHITECTURE.md` 2.2 / `DEVELOPMENT.md` 5.3

<a id="d-02-不用-rag只做原文关键词检索"></a>
## D-02 不用 RAG，原文检索用关键词搜索

**背景**：改编时需要从长篇原文中找相关段落。

**选项**：① 向量库 + 分块 + 检索；② 纯关键词搜索；③ 混合。

**决定**：选 ②。`app/agent/tools.py` 的 `search_source` 是纯文本搜索，`get_source_text` 按场景取原文片段。

**理由**：原文是**同一本书**——不存在跨文档的语义检索需求，用户问的也是"这段原文里怎么写的"，关键词命中足够。更重要的是：向量库要引入 embedding 服务、chunk 策略、调参、额外的失败面，而本项目的瓶颈根本不在"找得到哪段"，在"生成得对不对"。

**什么时候该推翻**：如果要做"从几十本参考书里找素材"这类跨文档检索，关键词就明显不够了。

**相关**：`app/agent/tools.py` · `app/pipeline/chunking.py`

<a id="d-03-编排用-langgraph-状态图而非多-agent-框架"></a>
## D-03 编排用 LangGraph 状态图，不引 CrewAI / AutoGen / Agno

**背景**：需要固定流程 + 中途人工干预 + 状态持久化。

**选项**：① LangGraph 状态图；② CrewAI / AutoGen / Agno 多 Agent 框架；③ 手写循环。

**决定**：选 ①。`app/agent/graph.py` 定义 7 节点固定编排，`interrupt` + `Command(resume=...)` 做审阅闭环，checkpointer 持久化。

**理由**：
- 我们的流程**是固定的**（context → plan → propose → guard → review → apply → finalize），不是"谁该接这个活"由模型决定。状态图把流程画在代码里，可读、可测、可断点。
- CrewAI/AutoGen 的抽象是"角色 + 任务 + 委派"，与我们的固定流水线不匹配，套上去反而更绕。
- 官方的 multi-agent research 系统（Anthropic，2025-06）实测多 Agent 成本是纯对话的 **15 倍 token**，换 90.2% 提升——对本地单机产品不可接受。

**什么时候该推翻**：如果产品形态变成"用户自定义一堆角色自由协作"，那 CrewAI 类的抽象才合适。

**相关**：`ARCHITECTURE.md` 三 · `DEVELOPMENT.md` 5.6

<a id="d-04-剧组的三个角色是函数不是-agent"></a>
## D-04 剧组的三个角色是「函数」，不是「Agent」

**背景**：系统里有导演 / 美术指导 / 摄影指导三个角色，各自产出结构化结果并被下游消费。

**选项**：① 每个角色做成一个嵌套 LLM 循环（有自己的工具、自己的上下文）；② 单次结构化调用。

**决定**：选 ②。`app/crew/base.py` 的 `CrewAgent.run()` 走 `self.llm.chat()` **一次**结构化调用，产出 `CrewTaskResult`。

**理由**：
- 三个角色是**流水线上的工位**，输入输出都已定型（剧本 → 分镜 → 提示词），它们不需要自主决策、不需要自己的工具、不需要多轮对话。
- 单次调用让每个角色的产出**可单独重跑、可单独审阅**（导演拆解不过就只重拆导演），这是流水线形态的关键优势。
- 成本与延迟都可预测。

**什么时候该推翻**：如果某个角色需要**回查上游、反复追问、或自己调用工具**，那它就该升级成独立 Agent。

**⚠️ 术语澄清**：这直接关系到业界"多 Agent vs 单 Agent"讨论——Anthropic 说的 subagent 指的是"有自己 context window、自己工具集、自己是嵌套 LLM 循环"的 Agent。**我们的三个 crew 角色不满足这个定义**，所以"把 subagent 折叠进主循环"那套改造对我们**基本不适用**，折叠成本接近零、收益也接近零。真正该借鉴的是其中两条通用原则：**长指令外置成 skill 按需加载**、**tool 按用户意图分组而非一个 API 一个 tool**。

**相关**：`app/crew/base.py` · `ARCHITECTURE.md` 3.2 / 3.4

<a id="d-05-确定性审计优先于-llm-评判"></a>
## D-05 确定性审计优先于 LLM 评判

**背景**：剧本与视频提示词需要质量把关。

**选项**：① 全部交给 LLM 打分；② 纯规则；③ 规则在前、LLM 在后。

**决定**：选 ③，且**规则层是主力**。`app/crew/dramaturgy.py` 把方法论里可代码化的部分全部落成纯字符串/字段运算：场景公式五要素、三细节律、五锚点、空洞词表（cinematic/epic/masterpiece 这类渲染不出来的词）、否定句检测（视频模型会把被否定的动作画出来）、台词引用检测。LLM 只在 `app/pipeline/review.py` 的五维评审里出现。

**理由**：规则判定**确定、可复现、零成本、零延迟**；LLM 判定会抖动、会烧钱、会"看情况"。而且规则能写进 `shot.prompt_audit` 让人逐镜核对。

**什么时候该推翻**：需要判断"这段情感是否动人"这类主观维度时，规则无能为力——但那时也只该**补** LLM 判据，不要替换规则层。

**相关**：`app/crew/dramaturgy.py` · `docs/DRAMATURGY.md` · `DEVELOPMENT.md` 5.5

<a id="d-06-前端不引-pinia--vue-router"></a>
## D-06 前端不引 Pinia / vue-router

**背景**：Vue 3 + Vite 6 单页工作台，三栏布局。

**选项**：① 引入 Pinia + vue-router；② 纯 `reactive()` 单例 store + 无路由。

**决定**：选 ②。`frontend/src/stores/app.js` 用 Vue `reactive()` 做单例 store，全项目无路由（单页工作台，左栏切换项目、右栏切 tab 都在同一个页面内）。

**理由**：产品形态就是**一个工作台**，没有多页面、多路由参数、面包屑、路由守卫的需求。引框架只增加学习成本和构建体积，换不到任何东西。

**什么时候该推翻**：一旦需要深链接（`/project/xxx/shot/yyy`）、多页面、或独立的分享页，就需要 vue-router。

**相关**：`frontend/src/stores/app.js`

<a id="d-07-数据库用-sqlalchemy-13-张表不拆微服务"></a>
## D-07 单库单表结构，不拆微服务

**背景**：需要持久化剧本、版本、镜头、视频任务、后台任务、记忆等。

**选项**：① 单个 PostgreSQL/SQLite 库；② 按域拆库；③ 微服务。

**决定**：选 ①。`app/store.py` 一套 SQLAlchemy 模型（13 张表），Postgres 与 SQLite 双支持（`DATABASE_URL` 切换）。

**理由**：本项目是**单机桌面级工具**（`API_HOST=127.0.0.1`，无鉴权），微服务带来的网络开销、部署复杂度、分布式事务，收益全为零。SQLite 让"克隆下来就能跑"成立——这对开源项目是硬指标。

**什么时候该推翻**：要多用户同时编辑同一项目、或要跨机器部署成服务时，先加鉴权，再考虑拆。

**相关**：`ARCHITECTURE.md` 一 · 技术债表（路由无鉴权）

<a id="d-08-视频统一-minimax-加用户自带-key"></a>
## D-08 视频生成统一 MiniMax，用户自带 Key 与模型名

**背景**：视频生成商众多（Kling / Runway / Sora / CogVideoX / MiniMax）。

**选项**：① 平台托管所有 key，按次计费；② 统一一家 + BYOK；③ 全部接入但都暴露给用户。

**决定**：选 ②。产品统一推 MiniMax，用户自带 key 与模型名（存 `api_providers.config_json.model`）。`app/video/providers/` 里 Kling / Runway / Sora / CogVideoX 的适配器**保留但不暴露**。

**理由**：视频生成是**唯一按 token 计费的大头**（MiniMax H3 实测 6s/768P ≈ 19.5 万 token/条）。让用户自带 key，项目方零垫资、零责任。用户想换厂商时，改一行 `config_json.model` 就行，不需要产品侧发版。

**2026-10-28 补充**：MiniMax 也接入了**对话**（`CHAT_PROVIDER=minimax`【该 env 已随 D-48 退役，现走设置→模型】，模型 `MiniMax-Text-01`），
于是**一把 key 打通对话 / 视频 / 配音**。代价是它的 `/chat/completions` 不支持
`response_format=json_object`（实测 2013），结构化输出要走降级路径（见
[`ARCHITECTURE.md` 2.5](ARCHITECTURE.md)）。这把 key 的价值在于**零配置可用**——
用户已经有 MiniMax key 的话，装完就能跑通全链路。

**什么时候该推翻**：要做"一站式付费出片"的商业化形态时，需要反过来做托管 key + 计费。

**相关**：`app/video/registry.py` · `DEVELOPMENT.md` 5.1

<a id="d-09-成片合成用-ffmpeg-命令行不引入-moviepy"></a>
## D-09 成片合成直接调 FFmpeg 命令行，不引 MoviePy

**背景**：拼接多镜、配音混音、ASS 字幕烧录。

**选项**：① FFmpeg 命令行直调；② MoviePy / PyAV 等封装库。

**决定**：选 ①。`app/video/assemble.py`、`app/media/dubbing.py`、`app/media/subtitles.py` 都是 `subprocess` 调 FFmpeg。依赖 `imageio-ffmpeg` 在系统没装 FFmpeg 时兜底提供二进制。

**理由**：
- 本项目的 FFmpeg 用法都是**滤镜图级别**的（`filter_complex` 混音、`subtitles` 滤镜烧录 ASS、concat 拼接）。MoviePy 的抽象在这几个场景里反而绕，因为它自己也是调 FFmpeg，只是多一层字符串拼接。
- 直接命令行 = 参数完全可控，遇到问题能直接查 FFmpeg 文档。
- 少一个重依赖。

**什么时候该推翻**：要做精细的帧级编辑或时间轴图形合成时，MoviePy 的 API 会更省事。

**相关**：`app/video/assemble.py` · `DEVELOPMENT.md` 5.7（未装 ffmpeg 的坑）

<a id="d-10-配音用云端-tts-暂不自托管"></a>
## D-10 配音用云端 TTS，暂不自托管

**背景**：视频模型产不出真实语音，台词必须由 TTS 单独合成再混进成片。

**选项**：① MiniMax T2A v2（云端，当前）；② 自托管（CosyVoice / F5-TTS / GPT-SoVITS）。

**决定**：当前用 ①。`app/llm/tts.py` 只有 MiniMax 一个实现。

**理由**：云端 TTS 音质稳定、无需 GPU、延迟低；自托管模型动辄几 GB 权重，对"克隆下来就能跑"的定位是重负。

**⚠️ 待复核的原因**：当前方案**强依赖外部 key**——没有 MiniMax key 就完全无法出片（合成失败会降级成"静片 + 估算字幕"）。

**候选（2026-10-28 调研，均已核实许可证）**：
- `FunAudioLLM/CosyVoice`（Apache-2.0）—— 官方提供 FastAPI server，接入方式与我们自建 provider 抽象完全契合。**注意：PyPI 上的 `cosyvoice` 包是别人 GPL-3.0 的复刻，必须用官方仓库。**
- `SWivid/F5-TTS`（MIT）—— pip 一行装，有 client-server 模式，接入成本最低。
- `RVC-Boss/GPT-SoVITS`（MIT）—— 中文克隆音色最强。
- **排除 `ChatTTS`**：AGPL-3.0，网络传染，提供网络服务会强制整个项目开源。

**什么时候该推翻**：如果要"零外部依赖出片"或面向完全离线的用户，开源本地通道应作为 fallback 接入。

**相关**：`app/llm/tts.py` · `app/media/dubbing.py`

<a id="d-11-字幕时间轴双源-配音实测优先否则字数估算"></a>
## D-11 字幕时间轴双源：配音实测优先，否则按字数估算

**背景**：字幕要贴在正确的画面上。

**选项**：① 强制先配音、用 TTS 实测时长；② 纯按字数估算；③ 双源降级。

**决定**：选 ③。配音开启时用 TTS 实测 track（`synthesize_track` 补 `speaker`/`end_ms`）；未配音时按「字数 / 4 秒」估算，且**在所属镜头窗口内**分配、不跨镜。

**理由**：字幕不准是成片最刺眼的缺陷。但强制配音会让"无配音成片"这条路径无法存在——而这恰恰是降级阶梯里需要的一环。

**⚠️ 前提条件**：估算只在镜头窗口内成立，**前提是镜头时长准确**。provider 实际产出与计划时长有偏差（v6 实测：计划 20s、成片 21.2s），所以 `finalize` 必须在下载后**逐镜实测校准**再排时间轴，否则越往后漂移越大。

**什么时候该推翻**：接入 ASR（whisperX / FunASR）做音频转字幕对齐后，可以直接拿词级时间戳，比估算精确得多。

**相关**：`app/media/subtitles.py` · `app/video/finalize.py`

<a id="d-12-长指令外置成-skill-自研加载器不引-deepagents"></a>
## D-12 长指令外置成 Skill：自研加载器，不引 deepagents —— 已定（2026-10-29）

**背景**：剧组三个角色的系统提示词加起来约 2.2 万字符，全部硬编码在 `.py` 里。三个后果：
① 改一条规则要改代码，非工程师改不了；② 改了什么、为什么改，混在代码 diff 里看不出来；
③ 一个 skill 无法单独评测、单独替换。

**选项**：① 引 `langchain-ai/deepagents`（MIT，30.7k★）的 `SkillsMiddleware`；
② 抄它的设计自研；③ 维持现状。

**决定**：选 ②。`app/skills/` 里 ~200 行加载器，零新依赖（用项目已有的 PyYAML）。

**为什么不是 ①**：`deepagents` 硬依赖 **LangChain ≥ 1.4.7**，我们锁的是 `langchain>=1.3,<1.4`，
要升依赖并经历迁移期双轨——为了一个 200 行就能实现的东西付这个代价不划算。
而且我们走 OpenAI 兼容 function calling，拿不到 Claude 原生的渐进披露，
**等价物本来就要自己实现**；既然要实现，按 Anthropic 的开放标准（SKILL.md + frontmatter）做，
比绑一个特定框架更稳。

**做法**：

| 层 | 实现 |
|---|---|
| 目录（第一级） | `skill_index()` 只给 name + description |
| 正文（第二级） | `load_skill(name)` / `render_skill(name, **vars)` |
| 附属文件（第三级） | `skill_file(name, filename)` |

已迁出的四个技能：`director-breakdown`、`video-prompt-zh`、`video-prompt-en`、`style-guide`。

**模板只支持两种语法**：`{{var}}` 替换、`{% if x %}…{% else %}…{% endif %}` 条件块。
**不用 `str.format()`**——提示词里全是 JSON 示例（`{"scene_id": ...}`），format 会把所有单花括号
当占位符直接炸。也**不支持嵌套条件块**：我们的用法就是「有锚/无锚」二选一，
支持嵌套只会让模板调试变复杂。

**缺变量必须报错**，不能静默留一个 `{{x}}` 在最终提示词里——那是比报错更糟的漂移。

**顺带正名**：`app/agent/skills.py` → `app/agent/tasks.py`。它从来不是 skill，
而是**后台任务运行器**（`SubAgentRunner`），挂在 `skills` 这个名字下是纯粹的术语污染，
会让后来的人误以为它就是技能机制。

**验证方式（这是重点）**：纯重构不能靠「看起来对」，要**逐字比对**。
迁移时先把旧实现的输出抓成基线，迁完后用新实现渲染同样的四种组合（中/英 × 有锚/无锚）
逐字比较——全部一致才继续。再跑 eval 确认质量指标没动：

| | 迁移前 | 迁移后 |
|---|---|---|
| 确定性层 critical | 0 | 0 |
| judge 均分 | 81.0 | 81.6 |

**收益（不是口号，是可验证的）**：
- 改写作规则只动 `.md`，git diff 干净，review 时不用在 Python 里找字符串；
- 每个技能可单独定位——`grep` 一句规则就能找到它属于哪个角色；
- 配合 D-13 的 eval，可以单独 A/B 某个技能的措辞。

**什么时候该推翻**：如果要让**主对话 Agent** 也按需加载技能（而不是像现在这样把 flow 指令
全写在 `SYSTEM_PROMPT` 里），需要再加一个 `load_skill` 工具 + 更细的触发条件。
那时可以重新评估是否直接换 deepagents。
→ **已按自研路线落地，见 [D-14](#d-14-主-agent-按需加载技能触发器留在提示词)**
（结论：仍不需要 deepagents；但触发器**不能**一起搬进技能）。

**相关**：`app/skills/` · `app/crew/{director,art_director,dp}.py` · `tests/test_skills.py`

<a id="d-13-提示词质量回归自建轻量框架"></a>
## D-13 提示词质量回归：自建轻量框架，不引 deepeval —— 已定（2026-10-28）

**背景**：现有 `tests/` 是 pytest 回归，测的是**代码不崩**，不是**提示词质量**。导演/摄影的输出质量只有运行时打分（五维评审）和成片视觉 QA，没有离线回归。改提示词没有编译器，只能靠出片后肉眼发现——太晚了。

**选项**：① `confident-ai/deepeval`（Apache-2.0，pip 原生）；② `promptfoo`（MIT，Node CLI）；③ 自建轻量框架。

**决定**：选 ③。实现在 `evals/`（独立于 `tests/`），分三层：

| 层 | 需要 key | 内容 |
|---|---|---|
| L0 单元 | 否 | 断言库自身、judge 解析器容错、case 完整性 |
| L0.5 离线回归 | 否 | 用**录制的真实产出**（`evals/fixtures/`）跑断言，锁住「不误报」 |
| L1 确定性 | 是 | 真实链路的分镜与提示词，规则判定，critical 必须为 0 |
| L2 judge | 是 | LLM 按五维量表打分，只看趋势 |

**理由（为什么没引 deepeval）**：
- 我们需要的判据**大部分已经是确定性的**——空洞词、否定句、引用台词、零细节、锚未复用，
  这些都能用正则判定，不需要 LLM-as-judge。deepeval 的价值主要在 LLM 判据上，
  而我们只需要它的一小块。
- deepeval 引入自己的 metric 抽象、dataset 格式与报告体系，要把这些映射到
  「导演分镜 / 摄影提示词」这个非常特定的领域模型上，适配成本高于自建。
- 提示词质量判定的**核心难点不是打分，是「判定规则本身对不对」**——这需要能直接读规则、
  能用录制产出做离线回归、能改单个断言并立刻看到影响。自建框架在这些点上更顺手。
- 少一个依赖。deepeval 会带进 torch 等一堆间接依赖。

**怎么借鉴的**：`zenstory-ai/drama-skills/evaluations/`（MIT）那套「rubric + judge prompt +
corpus + 质量门禁」的结构是直接照着来的，包括 judge 提示词里**要求每条扣分必须引用原文**
这条约束（用来压住 judge 的无据扣分与通胀打分）。

**关键设计约束**：
1. **judge 分数不参与红绿判定**——LLM 打分有抖动，10 条样本不够做统计判定。
   CI 只卡确定性的 critical 数。
2. **LLM 输出不确定**，即使把温度钉到 0 也不完全一致。对策：出现 critical 时
   **自动复跑一次**，两次都失败才算稳定缺陷。
3. **必须有离线回归层**。确定性断言最危险的失败模式是**误报**——一条假告警会让每个
   镜头都挂着警告，告警立刻失去意义。用录制的真实产出把「不误报」锁死。
4. **基础设施问题与质量失败分开计数**：余额不足 / 限流 / 鉴权失败归为 `blocked`，
   不算失败，但必须在报告里显式列出。跑不动不能被误读成「跑过了且通过」。

**它立刻回报了什么**（建完当天就跑出三个真问题）：
1. **生产审计器对真实提示词 4/4 全误报「一镜多运镜」**——风格段（全片运镜语法）被当成本镜运镜，
   且运镜动词没有镜头语境（「在地面拉出一道冷光带」里的「拉出」被当成 pull-out）。
   → 已修（`find_camera_moves` + `strip_style_block`），并补了回归测试。
2. **提示词里混进否定句**（「眼睛没有看任何地方」「避免均匀平光」「没有停留」）——
   视频模型会把被否定的内容照画出来。→ 已在美术指导与摄影指导的写作规则里补强，
   实测 critical 从 8 条降到 0 条。
3. **judge 的「克制度」维度只有 44.9 分**（五维里最低）——每镜都整段贴的全片风格段
   与本镜自己的光影/运镜描述打架。这不是 judge 偏差，是**视频模型真的收到了两套矛盾规格**。
   → **已修**（2026-10-28）：风格段改为「只补空、不覆盖」——body 已写光影/运镜就不再贴对应
   风格段，色调永远贴。实测 **克制度 47.0 → 72.9（+25.9）**、一致性 62.6 → 78.1、
   总体 **72.9 → 81.0（+8.1）**，确定性层 critical 归零。
   细节见 [`DEVELOPMENT.md` 5.13(6)](DEVELOPMENT.md)。
4. **角色出场却没带外观锚**——摄影指导的每镜人物列表偶尔漏人，导致画面里露脸的角色
   没有外观锚，跨镜长相漂移。
   → **已修**：`_apply()` 加确定性补漏（body 里点名的人必须有锚；没点名的不许塞进来）。

**这个 eval 的第一次实战结论**：三个真问题里两个已经修好并用数据验证，一个（否定句）
补了「交稿前逐句自查」指令后连续三次跑干净。**改建前先建 eval 是对的**——
否则这三个问题都只能等成片难看了才发现。

**什么时候该推翻**：如果将来要评的不是「本项目的提示词」而是通用 LLM 应用
（比如评问答质量、评 agent 选工具准确率），deepeval / promptfoo 的现成指标体系更划算。

**相关**：`evals/` · [`evals/README.md`](../evals/README.md) · `tests/test_dramaturgy.py`

<a id="d-14-主-agent-按需加载技能触发器留在提示词"></a>
## D-14 主 Agent 按需加载技能：触发器留在提示词，细则进技能 —— 已定（2026-10-29）

**背景**：D-12 把剧组三个角色的提示词外置了，但**主对话 Agent 的 15 条流程规则还硬编码在
`SYSTEM_PROMPT` 里**。D-12 的「什么时候该推翻」写的就是这件事：让主 Agent 也按需加载技能。

但直接照搬会错。先看清那 15 条是什么：它们是**路由信息**——用户说「出片」该调哪个工具。
路由每一轮都要用，把它搬进技能等于每轮多一次工具往返，而且模型一旦懒得加载就等于**不会做事**。

**真正的缺口不是提示词长，是提示词太薄**：「长篇小说」那条把五步流程（建图 → 提候选弧 →
按章选段 → 连载续接 → 汇报进度）压成了一句话；「出片」那条没写「指定镜头不走接力链」。
这些细则当时只存在于 `docs/` 和代码里，模型看不到，只能自己猜。

**选项**：① 全搬进技能（提示词只留一句「按需加载」）；② 触发器留提示词 + 细则进技能；
③ 维持现状。

**决定**：选 ②。分界线是：**「该做什么」留在提示词，「怎么做、什么顺序、什么会失败」进技能。**

**做法**：
- `SYSTEM_PROMPT` → `SYSTEM_PROMPT_TEMPLATE` + `system_prompt()`：触发器表（一行一条）+
  技能目录（`skill_index("main")`，只有 name/description/when_to_use）。
- 新增 4 个 `audience: main` 技能：`novel-serial`（长篇分段改编）、`crew-pipeline`（剧组四件事的
  依赖顺序与审阅边界）、`production-delivery`（批准到成片）、`script-review`（改编审阅闭环）。
- 新增 `load_skill` 工具：只能加载 main 技能，未知名字返回**可读提示 + 可用清单**而不是抛异常
  （工具抛错会污染当轮消息流，模型连改口的机会都没有）。
- `SkillMeta` 增加 `audience` 字段，`list_skills/skill_index` 支持按受众过滤。

**为什么不把剧组技能也列进主 Agent 的目录**：主 Agent 不执行分镜，列进去既是白付的 token，
也会诱导它去加载「导演分镜方法论」这种它根本不该执行的东西——**目录本身就是一种授权**。

**验证**：静态 14 条新测试（受众分组、目录不串味、触发器逐条指向真实工具、技能「相关工具」
必须是真工具、提示词预算 <2400 字、铁律不许丢）+ **真实模型路由实测**（DeepSeek，每例连跑 3 次）：

| 场景 | 期望 | 实测 |
|---|---|---|
| 「二十万字，直接生成完整初稿」 | 先加载 `novel-serial`，不直接生成 | 3/3 加载并拒绝直接生成 |
| 「把第 1 场对白改口语化」 | 加载 `script-review` | 3/3 |
| 「镜头都定好了，帮我出片」 | 只读盘点可以先查，动手前加载 | 3/3（查完 `list_video_shots` 后加载 `production-delivery` 再提交） |
| 「拆好了吗？」 | 不加载技能（纯盘点） | 3/3 只调 `check_background_tasks` |

提示词从 1890 字变 1748 字（含 4 行技能目录）；工具 22 → 23 个。

**第一次实测发现的问题（保留记录）**：最初的写法只有一句软要求「进入对应领域前先调
load_skill」，实测「出片」这条 0/3 加载——模型把它当成了「先查状态」而不是「进入领域」。
改成**按动作而非按领域**规定顺序（「本轮要动手，第一个工具调用就该是 load_skill；只读盘点可以
先查」）之后稳定 3/3。**软要求写不进概率模型的行为里，要么给顺序，要么给反例。**

**什么时候该推翻**：如果技能目录涨到十几条、提示词预算压不住，就该把目录也改成工具
（`list_skills` 先拉目录）——但那时要接受多一次往返。另外若将来有 agent 选工具准确率的
eval（D-13 提到的那类），「加载率」应该从人工实测升级成常驻指标。

**相关**：`app/chat/conductor.py` · `app/skills/loader.py` · `app/skills/{novel-serial,crew-pipeline,production-delivery,script-review}/SKILL.md` · `tests/test_chat.py` · `tests/test_skills.py`

## D-15 光源是分镜的硬信息，下游只能补方向不能换 —— 已定（2026-10-30）

**背景**：第一次跑通 judge 基线（10 条 case，平均 82.5，critical=0）。平均分本身没什么可说的，
有价值的是**两条 case 的连贯性维度塌了**：`chain_action` 37.5、`night_exterior` 55.0，
其余八条都在 93–95。judge 给出的证据指向同一件事：

> 「光线方向与前序信息矛盾：前序为右侧窗户午后斜阳，提示词改为右下方夜灯」
> 「前序为左前方洋红主光，提示词改为右前方粉绿主光」

**问题定性**：这不是「模型写得不好」，而是链路里把**硬信息当成了可再创作的信息**。
`Shot.lighting` 是导演/摄影在分镜阶段定下的物理事实（和风格锚一起决定「这场戏的光」），
DP 拿到它之后只该补方向、相对位置和运镜过程中的变化——**换掉光源就是换了一场戏的光**。
中文技能第 3 条当时只写「写清主光源是什么」，没有一句「不许换成别的」。

**决定**：
1. 技能层写死约束（中英各一份）：镜头方案给了光线就**沿用其光源与方位**，同一场各镜主光
   方向必须一致；只有方案没给时才允许自创，且自创后同场后续镜头继续沿用。
2. 检测层加三条（都是 `warn`，进 eval 也进生产审计器）：
   - `DPT-13` 光源被换掉（窗光 → 台灯这类互斥光源）
   - `DPT-14` 光位方向相反（左 → 右）
   - `DPT-15` 同一句写了两遍
3. 顺手修了 `DPT-15` 命中的真 bug：`dp.py` 的「最终画面兜底」用
   `_norm_key(final_frame)[:8] in body` 判断模型写没写，模型只要换个开头就被判成没写，

   改为滑窗覆盖率（4 字窗 ≥60% 或 2 字窗 ≥65%）。

## D-16 多把 key 并存轮换，不做单 key 硬绑定 —— 已定（2026-10-30）

**背景**：视频/配音链路的 key 一欠费，整条出片链路直接死掉（实测旧 key 打
`/v2/video_generation` 返回 402 `insufficient balance (1008)`），而人手上改 `.env`
+ 重启进程是唯一出路。同时，同一个厂商出现多把 key 是常态：换账号、新旧并存、
免费额度与付费额度分开算。此时「配置里只能有一个 `MINIMAX_API_KEY`」就是在逼
人做无意义的取舍。

**选项**：① 只留一把 key，欠费就手动换；② 写死主备两把 key，主 key 失败才切；
③ 通用 key 环：可配任意多把，按可用性挑一把，失效的进冷却。

**决定**：选 ③，落在 `app/keys.py`（`KeyRing` / `ring_for` / `minimax_keys`），
视频 Provider 与 TTS 客户端共用同一份 key 环；对话链路只在开局取「最该用的那把」。

**理由**：
- **区分「key 坏」和「请求坏」是本功能的全部价值**。只有 401 / 402 / 403 与响应体里的
  `(1004) 鉴权失败`、`(1008) 余额不足` 才换 key；`(2013) invalid params` 这类参数错误
  换 key 也没用——天真实现会把一次笔误当成 key 失效，把能用的 key 全判死十分钟。
- **冷却而不是删除**。充值后不该重启进程，`KEY_COOLDOWN_SEC`（默认 600s）到期自动复活；
  全在冷却期时仍按最早恢复的顺序兜底尝试，宁可赌一把也不直接报错。
- **顺序即优先级**。先写的先用，与「我正在用哪把」的心智模型一致；不用随机/轮询，
  否则出问题时分不清是配置问题还是运气。
- **跨账号查询要认领**。视频任务是账号级资源：用 A 账号提交、B 账号去查会拿到
  `2013 invalid task_id`。所以提交时把 `task_id → key` 记下来（`MiniMaxProvider._TASK_KEYS`），
  轮询绑定同一把；查询遇到 2013 只换 key 继续查，**不冷却**——那把 key 是好的。

**验证**（真实额度，非打桩）：
- 新 key 四项能力全通：H3 出片（4s/480P，约 2 分钟出片、461KB mp4 可播）、
  `MiniMax-Text-01` 对话、`speech-02-hd` 配音、`image-01` 文生图；
- 故障演练：故意把已欠费的 key 放第一位提交，日志记 `进入冷却 600s：insufficient balance (1008)`，
  自动切到备用 key 出片成功（`task 457902515176056` → succeeded）；
- `tests/test_keys.py` 16 条：误判（参数错不换 key/不冷却）、漏判（402/401 必换）、
  串号（2013 回到正确账号）、配音轮换、冷却复活、空配置不炸；
- 全量 `pytest` 264 passed。

**什么时候该推翻**：如果哪天 key 变成了「按任务计费、可预扣」的模式，需要的是配额
预留而不是失败后切换；或者接入的厂商开始支持「一个 key 多账号池」，那 key 环就该换成
厂商侧的配额管理。

**相关**：`app/keys.py` · `app/video/providers/minimax.py` · `app/llm/tts.py` ·
`app/llm/registry.py` · `tests/test_keys.py` · `.env.example`

## D-17 分镜必须「可执行」，台词必须落位：把软要求变成硬断言 —— 已定（2026-10-31）

**背景**：拿鲁迅《孔乙己》真跑一遍完整链路（导入 → 剧本 → 分镜 → 提示词 → 出片 → 合成），
成片出来后用户的原话是「声音和动作都很乱」「声音和动作不搭配，完全不知道是谁和谁说的」。
逐层拆开，三处都不是玄学，而是可复现的机制问题：

1. **出片时长写死 6 秒**。`_create_and_submit_job` 里 `duration = params.get("duration_sec") or 6`，
   导演在分镜里设计的 8 秒、10 秒镜头，只要调用方没显式传时长，一律按 6 秒送进模型。
   动作被硬塞进更短的时间，模型只能丢节拍、把姿势糊在一起。
2. **台词归属的兜底写反了**。`plan_dubbing` 里只要有一个镜头填了 `dialogue_ref`，就进入
   「引用优先」分支，而该分支把**所有**没被引用的台词塞给 `next(iter(ref_to_shot.values()))`
   ——同一场戏的第一个引用镜。于是画面里酒客在笑，声音却是孔乙己在说话。
3. **台词没有时间概念**。`synthesize_track` 里每句台词一律排在「镜头起点 + 0.4 秒」，
   同镜多句顺序堆。画面上人还在摸钱，声音已经在说下一句。
4. **导演分镜没有动作预算**。九镜全部超标：8–10 秒里写 3–6 段连续动作、最长一句 89 字，
   而校验只管「时长 4–15 秒」。技能文件里明明写了「一镜只有一个主事件」和「对话时长
   ≥ 字数 ÷ 4」，但那是**软要求**——模型照样不照做（与 5.14 同一条教训）。

**选项**：① 只在配音层做后处理（按字数重排时间）——治不了「台词找错镜头」和「一镜五动作」；
② 让用户在界面里手工调每一镜的时长和台词——把问题推给人；③ 把分镜的可执行性做成
**确定性断言**（不满足就打回重拆）+ 给台词一个**镜头内的落位字段** + 修掉时长传参。

**决定**：选 ③。

- **`app/video/rhythm.py`**：节奏基准时长 slow 8s / medium 6s / fast 4s，另有 `suggest_ladder`
  给「长 → 渐短」的阶梯建议。出片时长优先级改为
  **调用方显式指定 > 导演给该镜的 `duration_sec` > 节奏默认值**，并把最终值写回落库 params
  （重试、批量重投口径一致）。
- **`Shot.dialogue_at`**：台词在镜头内第几秒开口。导演拆镜时必须写，配音层按它落位
  （夹在本镜范围内，绝不让声音盖到下一镜的画面上）。
- **`assign_dialogue_ranges`（`app/domain.py`）**：按 `dialogue_ref` 的分界点把台词切给各镜，
  一镜只拿「从它引用的那句起、往后同一个说话人连续说的几句」，换人就断开。断言与配音
  共用这一份口径——否则会出现「断言说对了、配音还是错的」。
- **导演硬断言**（`_validate_continuity`）：动作分句数 ≤ `max(3, 时长/3)`；一句台词要念得完
  （字数 ÷ 4 + 0.2 ≤ 时长）；每句台词都必须落在某个镜头的范围内。
- **critique 限量回喂**：一次只把最要紧的 5 条丢回给模型，其余下一轮再说。

**踩坑记录（都是真跑出来的，别再踩）**：

- **「多主体」判据是错的**。一开始想抓「一镜里三个人各动各的」，用「角色名在 action 里出现
  几次」来判——但正则分不清「甲指着乙」和「乙在做动作」，`酒客甲下巴朝孔乙己一抬` 会被判成
  两个主体在动。它让导演白改三轮，还把一个本来合格的版本改坏。**已撤回**：机械层只兜底
  「明显塞太满」，语义判断交给规则本身。
- **批评给太多，模型越改越散**。把 11 条批评一次性回喂，镜头数从 10 涨到 11、问题从 2 条涨到
  7 条。限量 5 条之后才收敛。
- **「分号段数」不等于「动作数」**。`把碗搁在柜台上；下巴一抬；手指点过去` 是一个动作的三笔
  细节。所以阈值下限给 3 段，不是「一镜最多 2 个动作」。

**验证**：
- 旧分镜回放新断言：**9 镜全部动作超标、13 段对话没有镜头认领**——证明成片乱是分镜本身就
  不可执行，不是渲染运气差。
- 重拆 scene_002：10 镜，硬约束全过；台词归属变成 6 句一人一镜且顺序正确
  （酒客甲嘲讽 → 孔乙己点酒 → 酒客乙补刀 → 孔乙己辩解 → 酒客甲追问 → 孔乙己「窃书不能算偷」）。
- 出片落库核对：`duration_sec=8`，不再是写死的 6。
- 测试 269 → 283 passed（新增 `tests/test_director_guard.py` 9 条、配音归属与落位 5 条、
  时长传参 2 条）。

**什么时候该推翻**：如果哪天视频模型能稳定处理「一镜多动作 + 多主体对话」（比如自带口型
同步与分镜级时序控制），这套「一镜一主事件、一镜一说话人」的硬约束就该放宽——它是为当前
生成能力付的保险费，不是美学主张。

**相关**：`app/crew/director.py` · `app/domain.py` · `app/media/dubbing.py` ·
`app/api/video.py` · `app/video/rhythm.py` · `app/skills/director-breakdown/SKILL.md` ·
`tests/test_director_guard.py` · `tests/test_dubbing.py`

<a id="d-18-角色到声音必须显式可查不许运行期猜"></a>
## D-18 角色到声音必须显式可查，不许运行期猜 —— 已定（2026-10-31）

**背景**：《孔乙己》成片里，酒客甲、酒客乙、「我」开口全是御姐音，孔乙己本人是霸道男声。
用户的原话是「女声音的角色从男角色嘴中出来了」「不知道是谁和谁说的」。

根因是 `assign_voices` 的兜底逻辑：先按关键词猜女声，剩下的角色用一个
`alternation = [FEMALE_MATURE, MALE_MATURE]` 列表按出场顺序**男女交替**发声音。
这个列表**从女声起头**，于是全片第一个推断不出性别的角色必然拿到御姐音——孔乙己的
五个角色里有四个都是这么来的。复现结果：

| 角色 | 旧逻辑 | 新逻辑 |
|---|---|---|
| 酒客甲 | `female-yujie`（女） | `male-qn-badao` 磁性男声 |
| 掌柜 | `male-qn-badao` | `male-qn-jingying` 精英男声 |
| 酒客乙 | `female-yujie`（女） | `male-qn-daxuesheng` 学生男声 |
| 孔乙己 | `male-qn-badao` | `male-qn-badao` 磁性男声 |
| 我 | `female-yujie`（女） | `male-qn-daxuesheng` 学生男声 |

还有第二层伤害：旧代码对「剧本里没有的人」一律 `voices.get(name, VOICE_MALE_MATURE)`，
一群人共用一把嗓子，观众当然分不清谁在说。

**选项**：① 继续加强关键词规则（性别词、名用字、代词）——永远会猜错，且错了没人看得见；
② 把「角色→音色」做成**资产库里的显式字段**，推断只做兜底，并把推断依据显示在界面上；
③ 让用户每部片手动指定每个角色的音色——把劳动推给人。

**决定**：选 ②，并且把兜底方向改对。

- **`app/media/casting.py`**：六档优先级——显式选角 > `Character.gender` > 名字称谓 >
  描述代词 > 女性名用字（弱证据，标记为推测）> **默认男声**。
  默认必须是男声：中文短剧绝大多数角色是男性，且「女声从男人嘴里出来」比「女角色用男声」
  刺耳得多。没有线索的角色会进 `warnings`，明确告诉用户「这些是猜的，可以改」。
- **挑音色的顺序**：主角 → 反派 → 配角，同档按**台词字数降序**。因为剧本阶段常把所有人
  一律标成 `supporting`（实测《孔乙己》五个角色全是），只按 role 排等于没排；戏份最重的人
  先挑，比 role 更可靠。池子满了以后溢出的人复用**池尾**（不是池首），避免和主角撞声。
- **`Character.gender`**：新增字段，剧本阶段可直接标注，人工修正优先于一切推断。
- **资产库**（`app/media/library.py` + `app/api/cast.py` + 前端 `CastLibrary.vue`）：
  一张表同时给出「角色 → 外貌锚 / 定妆图 / 性别（含依据）/ 音色（含依据）/ 台词量」，可改、可试听。
  数据仍存在项目 `video_style_json` 里（复用 `reference_images`、`character_appearances` 的键体系，
  只加 `voice_casting` 与 `character_genders` 两个键），不新建表。

**顺带修掉的隐患**：美术指导原先用 `set_video_style` 整体覆盖风格 JSON，会把资产库里人工
指定的音色一并冲掉；改成 `merge_video_style`。

**什么时候该推翻**：如果 TTS 支持零样本音色克隆（拿角色参考音频定声线），「选一个系统音色」
就该升级成「克隆一个音色」，但「角色→声音必须显式可查」这条不会变。

<a id="d-19-短剧包含漫剧画风是正交维度不是第六种类型"></a>
## D-19 短剧包含漫剧：画风是正交维度，不是第六种类型 —— 已定（2026-10-31）

**背景**：产品上要区分短剧与漫剧。第一反应是把「漫剧」加成一个新的 `AdaptationType`，
和 `short_drama` 并列。但这两个词不在同一根轴上：

- **短剧**按「载体 + 时长 + 分发」定义：竖屏、单集 1–2 分钟、前 3 秒抓人、按完播/付费投流。
  它的对面是电影、长剧集。
- **漫剧**按「画风 + 呈现介质」定义：二次元、分格构图、符号化表演。它的对面是实拍短剧。

所以漫剧是短剧赛道里的**画风子类**，不是另一个体裁——它用的还是同一套分发逻辑、同一套
付费模型、同一套节奏。用户的原话也印证了这点：「我感觉只有画风上的差距」。

做并列类型的代价很具体：导演拆镜、节奏取值、连续性校验、profiles 全要为一个画风分叉，
而画风真正只影响三件事——**定妆图 prompt（立绘还是剧照）、提示词的画风声明、配音气质**。

**选项**：① 加 `anime_drama` 类型（试过，已回退）；② 类型收敛为 `short_drama`，另加正交的
`visual_style` 维度；③ 完全不做区分，一个画风打天下。

**决定**：选 ②。

- **`app/domain.py`**：`VisualStyle = realistic | anime | 3d | ink`，挂在 `StyleGuide.visual_style`
  上，与 `AdaptationType` 相乘，不做组合爆炸。
- **`app/pipeline/visual_styles.py`**（新）：每个画风四段可直接进 prompt 的文本——
  `render_note`（提示词画风声明）、`character_sheet`（剧照 or 立绘）、`environment_sheet`
  （空镜 or 背景美术）、`negative`（画风反例）。**写 prompt 必须说「二维动画」而不是「动漫风格」**，
  后者会让视频模型理解成「有点动画感的实拍」。
- **`app/video/rhythm.py`**：删掉 `anime_drama` 档位。漫剧不需要独立节奏表——它就是短剧。
- **`app/media/casting.py`**：`voice_pools(visual_style)`，二次元/三维用年轻音色池（少年/少女优先），
  实拍/水墨用写实池。这不是「另一个类型」，只是同一套池子的优先级不同。
- **导演层**：画风不改节奏，但改镜头语法——二维画面在大幅运镜时结构容易崩，prompt 里
  要求「固定机位、小幅推近、角色局部动作，少用环绕与快速摇移」。
- **产品层**：新建项目时「改编类型」只突出短剧，「画风」单独一排芯片（实拍 / 二次元(漫剧) /
  三维 / 水墨）。用户选「二次元」就是做漫剧，不需要理解类型与画风的关系。

**什么时候该推翻**：如果漫剧发展出与短剧**不同的分发形态**（例如必须按「页」付费、
必须一次放出整季），那它就不再是画风子类，应该独立成类型。

**相关**：`app/pipeline/visual_styles.py`、`app/domain.py`、`app/media/refs.py`、`app/crew/director.py`

<a id="d-20-产品只留一条链路小说到短剧其余全砍"></a>
## D-20 产品只留一条链路：小说 → 短剧，其余全砍 —— 已定（2026-11-01）

**背景**：项目早期按「剧本工作台」的通用形态铺开——支持电影 / 剧集 / 舞台剧，
内置 Runway / Kling / CogVideo / Sora 四家视频适配，还留了一套 3D blockout 资产。
真跑《孔乙己》全链路才发现：这条主链路本身还很脆——拆镜会因输出截断整批作废、
片长会失控到 5 分钟、音色能把男角色配成御姐音、批量出片会被 429 全歼。
而上面那些「将来可能用到」的分支，一个都没有被真实使用过。

**选项**：① 继续铺广度，等基础能力齐了再打磨深度；② 收成一条链路，把所有注意力
压在这条链路的质量上；③ 保持现状，两边都不动。

**决定**：选 ②。

- **类型只留短剧**：`profiles.py` 删掉 film / series / stage 三份（-45 行）。
  `domain.AdaptationType` 保留这些枚举值，只为读得动历史数据，不再对外提供入口。
- **视频只留 MiniMax**：删四个从未启用的 provider。要加新厂商时按 `base.VideoProvider`
  实现一个模块、在 registry 注册一行即可——接口已经稳定，不需要提前占位。
- **删 `blender/`**：6 个 3D blockout 资产，与小说→短剧链路无关。
- **对外名称改为「问剧」**：产品定位从「剧本工作台」变成「小说转短剧工具」，
  名字跟着收窄。Python 包名不改（改包名只有成本没有收益）。

**理由**：旁支的成本不是它占的那点代码，而是**每次改核心接口都要回来照顾它**——
`VideoProvider` 加一个字段，四个没人跑的适配器也要跟着改；多一个改编类型，
生成提示词、校验、测试就多一套分支。这些成本是持续的，收益是假设的。

**什么时候该推翻**：当短剧这条链路稳定到「连续 10 部小说能出 10 部合格短剧」，
再考虑横向扩展才有意义。届时的扩展应该是**加画风**（已在 D-19 做了维度），
而不是加体裁。

**相关**：`app/pipeline/profiles.py`、`app/video/providers/`、`README.md`

## D-21 查询只留一个入口，技能里的工具名必须和代码对齐 —— 已定（2026-11-01）

**背景**：主 Agent 一度有 23 个工具，其中 5 个都是「查状态」——
`get_script_overview` / `list_video_shots` / `get_video_jobs` / `check_finalize` /
`check_background_tasks`。它们查的是同一个项目的不同侧面，边界靠描述文字区分。

真跑时出过一次：Agent 说「项目里根本没有镜头方案」，而同一个数据用
`list_video_shots` 直接查得到 62 镜。**工具太像，模型选错一个，就会拿另一个工具的
空结果当成事实**——这比工具数量多更贵，因为它是「一本正经地说瞎话」。

**选项**：① 保留 5 个，把描述写得更细；② 合并成一个，用参数区分粒度；
③ 每个查询做成资源路由（`/status/shots` 这类）。

**决定**：选 ②。

- `get_status(project_id, detail="summary|shots")`：默认给概况（剧本 / 镜头 / 已批准 /
  已出片 / 失败数 / 后台任务 / 合成），`detail="shots"` 才展开逐镜清单。
- 顺手把「技能里点名的工具必须真实存在」变成测试
  （`tests/test_skills.py::test_skill_tool_refs_exist`）——这次合并改了 4 个 SKILL.md
  才补干净，而漏改**不会报错**：模型读到「先调 `list_video_shots`」，那个工具已经不存在，
  它要么换一个不对的、要么凭印象编进度。

**理由**：工具数量的成本不在 schema 长度，在**模型选错的概率**。5 个语义重叠的查询工具，
选错一次就足以让用户看到假结论。合成一个之后，「查询」这件事没有第二种做法。

**一个反直觉的发现**：查询类工具合并后，模型输出「我不知道」的次数明显下降——
因为过去它常常查到一半就下结论（用错工具拿到空结果）。**少一个选择，反而少一次幻觉。**

**什么时候该拆回去**：当 `detail` 的取值超过 3–4 个，说明它已经变成「万能工具」，
那时按资源拆成独立端点比继续堆参数更清楚。

**相关**：`app/chat/conductor.py`、`tests/test_skills.py`、`docs/ARCHITECTURE.md` 三·3.1

<a id="d-22-资产一律按实体-id-索引名字只是别名"></a>
## D-22 资产一律按实体 id 索引，名字只是别名 —— 已定（2026-11-01）

**背景**：角色的五份资产（外貌锚 / 环境锚 / 定妆图 / 音色 / 性别）全部以**中文名**做键：

```python
character_appearances: {"孔乙己": "四十岁上下……"}
reference_images:      {"孔乙己": "https://…"}
voice_casting:         {"孔乙己": "male-qn-badao"}
character_genders:     {"孔乙己": "male"}
```

名字是模型随手写的，也是用户随时会改的。改一次名，四份锚点同时失联——**而且不报错**：
查不到就当没有，定妆图不出、音色回落到推断、外貌锚消失。表现是「后半部每镜都像换了
个人」，但没有任何一处抛异常，只能靠人肉比对。这是长篇跑偏最贵的那个原因。

**选项**：① 名字做键，改名时级联更新四处（写一段改名事务）；② 按 id 存，名字只作显示；
③ 新加一张 assets 表，用外键约束。

**决定**：选 ②。

- 新增 `app/media/assets.py`：`rekey()`（名字键 → id 键，幂等）、`lookup()`（读时两种键都认）、
  `as_name_map()`（拼提示词时转回名字）、`build_index()`（剧本里的 id ↔ 名字索引）。
- **模型照旧写名字**，落库前由代码映射成 id（`art_director._parse_guide`）。让 LLM 直接
  输出 `char_004` 的准确率很低，写错就是静默丢锚点——**格式该由代码保证，不该指望模型**。
- 老数据**不做一次性迁移**：读取路径兼容名字键；用户第一次改资产时整份表顺手规整成 id 键。
- 重名不猜：同名角色 `resolve()` 返回 None，键原样保留（猜错等于把 A 的脸贴 B 身上）。

**理由**：③ 要多一张表 + 外键 + 迁移脚本，而资产本质是「项目的属性」，不是独立生命周期
的实体；① 的级联更新是「每个写入点都要记得更新四处」，漏一处就静默丢——正是现在这个 bug
的放大版。② 把「名字→id」的转换收敛到**两个边界**（落库、拼提示词），中间全程用 id。

## D-23 用户数据全部存数据库，本地不落成品文件 —— 已定（2026-11-02）

**背景**：产品定位向「网页版 AI 视频工具」看齐，用户明确要求「本地不留文件，全部用户数据
存数据库」。此前状态：元数据在 Postgres，但媒体文件本体（上传素材、成片、SRT）落盘在
`data/assets/<project_id>/`，工作区镜像目录（01_原稿/02_版本/03_导出/04_知识库）也写磁盘。

**决定**：

1. **媒体文件本体入库**：`media_assets` 表新增 `content BYTEA` 列。上传（`assets.py`）与
   成片/SRT 登记（`finalize._register_asset`）都改为字节入库，本地不落成品文件。
   回放端点优先读 DB，对历史 `file_path` 记录向下兼容。合成/配音过程中的**临时文件仍然
   本地**（ffmpeg 要求文件路径），finalize 完成即清理——「本地不留」指最终产物，不是过程。
2. **工作区镜像默认关闭**：`.env` 设 `WORKSPACE_PERSIST=false`（in_app 模式），
   01_原稿等镜像目录不再写盘；文本数据本来就在库里。
3. **存量迁移**：`scripts/migrate_assets_to_db.py` 一次性把 DB 登记过的磁盘素材读入
   （实际只有 2 条，约 1.7MB）；`data/assets/` 下 35MB 为临时测试库遗留的孤儿文件，直接删除。
4. 200MB 单文件上限不变；Postgres TOAST 足够覆盖当前规模（单镜成片 ~1-6MB）。

**后果**：数据库成为唯一事实源，备份 = 备份数据库；数据目录不再无限膨胀。
代价是 DB 体积随素材增长（可接受），且回放响应无 Range 支持（预览够用，拖动进度条
需整段加载——将来要精剪时再考虑分块或对象存储）。

**相关**：`app/api/assets.py`、`app/video/finalize.py`、`app/store.py`（MediaAsset）、
`app/workspace.py`（persist=in_app）、`scripts/migrate_assets_to_db.py`

<a id="d-29-对话内核脱离-langgraph改成显式-while-循环"></a>
## D-29 对话内核脱离 LangGraph，改成显式 while 循环 —— 已定（2026-11-05）

**背景**：对话 conductor 用 LangGraph 的 `StateGraph` + `ToolNode` 跑 ReAct 循环。三个具体痛点：
① 状态通道（reducer）行为不直观——踩过 `has_images` 这类键在节点之间丢失的坑；
② 循环本来就是「LLM → 工具 → LLM」，画成图反而要多读一层才知道发生了什么；
③ 调试是黑盒：出问题时看不到「第几轮、调了什么工具、回了什么」。

**选项**：① 继续用 StateGraph；② 换成 LangChain 的 `AgentExecutor`；③ 自研显式循环。

**决定**：选 ③。`app/chat/loop.py` 约 250 行：

```
for step in range(max_steps):        # 上限 8 轮
    resp = model(messages, tools)
    没有 tool_calls → 结束
    for call: 执行工具 → messages.append(tool 结果)
```

**消息协议**：OpenAI 兼容的 dict（`role` / `content` / `tool_calls` / `tool_call_id`）。
我们所有 provider（DeepSeek / 智谱 / OpenAI / Qwen / MiniMax）都是这个协议，
所以**协议本身就是通用格式**，不绑任何框架类型。

**LangChain 只保留一处适配**：`_to_lc_messages()` 在「真正调模型那一刻」把 dict 转成
LangChain 消息。将来换成自写 HTTP provider，只需要替换这一个函数——内核、工具、事件、
conductor 全都不用动。

**为什么现在不一步到位写 HTTP provider**：`ChatOpenAI` 已经处理了流式解析、重试、
`extra_body`（DeepSeek 关思考）、`base_url` 切换。这些重写一遍没有收益，反而引入新的
失败面。先把「图」这个真正的痛点去掉，transport 留到真有需要时再换——因为边界已经画好了。

**工具协议**：沿用 LangChain 的 `@tool` 对象（`.name` / `.description` / `.invoke(args)`），

<a id="d-30-技能拆分用消融对比验证而不是靠论证"></a>
## D-30 技能拆分用「消融对比」验证，不靠论证 —— 已定（2026-11-06）

**背景**：主 Agent 的四个技能（`novel-serial` / `crew-pipeline` / `script-review` /
`production-delivery`）是按阶段拆开的。拆完有人问：**拆开到底有没有用？**
「有触发器表在系统提示里就够了吧，技能正文是不是多余的」——这是个合理质疑，
光靠设计论证回答不了。

**决定**：建 `evals/skill_eval.py`，用**消融对比**（ablation）回答。

**方法**：同一批用例跑两遍——
- **有技能**：`load_skill` 可用，Agent 能拉到 SKILL.md 正文；
- **无技能**：把 `load_skill` 从工具集里摘掉，Agent 只能靠系统提示的触发器表。

两组的**约束落地率**之差 = 技能正文的真实价值。因为系统提示本来就有
「意图 → 工具」的触发器表，所以光看「调对工具」证明不了什么；
能证明的只有那些**只在技能正文里写的硬约束**（依赖顺序、批准前置、防静默截断）。

**实测（5 条用例 × 3 次重复 × 2 条件 = 30 次对话）**：

| 用例 | 有技能 | 无技能 | 差 |
|---|---|---|---|
| `crew_order`（依赖顺序） | 15/15 | 6/15 | **+60%** |
| `long_novel_truncation`（防静默截断） | 8/12 | 6/12 | +17% |
| `delivery_before_approve`（批准前置） | 13/15 | 11/15 | +13% |
| `revision_not_direct_edit`（提议而非改稿） | 5/9 | 4/9 | +11% |
| `no_over_trigger`（反向：不该加载） | 6/6 | 6/6 | +0% |
| **合计** | **47/57 = 82%** | **33/57 = 58%** | **Δ +25%** |

**结论**：技能正文有可观测价值（Δ +25%），**价值集中在「带硬约束」的地方**——
`crew-pipeline` 的依赖顺序一条就值 +60%（无技能组只拆解就停了，链条断了）。
反向用例 0% 差异，说明拆分没有引入过度触发。

**三个必须记住的坑**（都写进了 `tests/test_skill_eval.py`）：

1. **「尝试加载」≠「加载成功」**。消融组里工具不存在，但系统提示写着
   「本轮第一个工具调用就应该是 load_skill」，模型照样会**尝试**调用，
   循环返回「未知工具：…」。第一版 harness 把尝试当成成功，
   导致消融组显示「技能被加载了」——测量直接失效。
2. **用例必须让领域动作可执行**。没有剧本时 Agent 只能回「还没有剧本」，
   测出来的是「它知道自己没剧本」，不是「技能引导了它」。
   所以每条用例要按需预置剧本 / 待批准镜头。
3. **单次结果方差大到不能下结论**。同一用例不同轮次会做出不同选择
   （温度 0 也不保证逐字一致）。必须 `--repeat 3` 以上看聚合。

**什么时候该推翻**：如果把技能正文里的硬约束都搬回系统提示，
那 Δ 会趋近 0——那时技能就只剩「省 token」这一个价值，
是否还值得拆成四份就要重新算账。

**相关**：`evals/skill_eval.py` · `evals/skill_cases.py` · `tests/test_skill_eval.py` ·
`app/skills/*/SKILL.md`

## D-33 对话里用 @ 引用资产，提示词里也用同一套语法 —— 已定（2026-11-08）

**背景**：用户 2026-11-08 提了两件事：① 要能用 @ 引用资产库里的内容；
② 我们的大模型生成的提示词也要学会用 @ 引用资产。

**决定**：
- **对话侧**：输入框打 @ 弹出候选（角色 / 场景 / 成片参考素材），选中插入 `@名字`；
  引用清单随请求发给后端（`ChatRequest.refs`），本轮上下文里附
  「【本轮引用的资产】」列出类型 + 编号 + 名字。
  只写「@林然」三个字，Agent 不知道它是哪部作品里的哪个角色——编号必须带上。
- **提示词侧**：视频提示词里的资产标记从 `［资产:char_xxx］` 改成 `@名字(编号)`。
  与用户在对话里的写法同一套语法；没有编号就不标（归属不明的锚不硬标）。
- 系统提示新增第 0 条规矩教 Agent @ 的语义（被 @ 到的就是本轮要处理的对象）。

**理由**：同一套引用语法贯穿「人怎么说话」和「提示词怎么写」，用户不用学两套；
编号让人能顺着找到资产库条目（换一张定妆图要影响所有引用它的镜头）。

**什么时候该推翻**：如果提示词最终交给的模型对 @ 符号敏感（部分视频模型会把 @ 读成
at-mention 语义），则提示词侧需要再转回中性的标记形式——但对话侧的 @ 保留。

## D-36 借鉴 mediago-drama：只移植具体手法，不换 Agent 内核 —— 已定（2026-11-09）

**背景**：`mediago-dev/mediago-drama`（Apache-2.0）是目前能读到的、最接近「漫剧 Agent 工作台」

① 整体照搬它的架构（换成 Codex app-server + cwd 即上下文 + 文件型文档树）；
② 只移植具体手法，不动内核；
③ 不参考，继续自研。

- **不换 Agent 内核**——不引入 Codex app-server。它的价值在于「有个现成的成熟 Agent」，

  1. **提示词写法**（6 条，见 PLAN B 组）：抗绕过句式、不要编造 ID 清单、

  2. **生成授权闸门**：提交幂等 + 意图指纹 + 一次性 claim + 失败不释放。
- **明确不采纳它的短板**：它的 Skill 全靠提示词自律、没有任何代码校验。
  我们有 D-05（能用规则判的绝不用 LLM 判）与 D-13（自建质量评测），

<a id="d-37-参考视频只从参考素材里选不再收公网直链"></a>
## D-37 参考视频只从「参考素材」里选，不再收公网直链 —— 已定（2026-11-10）

**背景**：提示词审阅器里有个「参考视频 ≤3 条公网 URL」的输入框，让用户手填
mp4 直链。这条路有两个问题：

1. **和「参考素材」这个统一入口打架**。用户明明已经在资产库里导入了白模 /
   previz，却还要去别处找一条能公开访问的直链再手抄一遍。资产库里的素材
   是**本机文件**（存在 `media_assets.content`，对外只有 `/api/assets/file/xxx`
   这个相对回放地址），服务商在云上根本拉不到——所以「手填公网直链」其实是被
   服务商的限制逼出来的 workaround，不是好设计。
2. **多一条路就多一份不一致**。素材有来源（上传 / 公网登记 / 成片），参考视频
   却另开一个口子，两边的清理、权限、体积限制全对不上。

**选项**：
① 保留手填公网直链，另加一个「从素材里选」；
② 只保留「从素材里选」，把公网直链那条路整条拆掉；
③ 两条都留，但把公网直链收进资产库的一个入口。

**决定**：**选 ②**。具体边界：

- **参考视频只有一个来源：参考素材**。提示词审阅器里改成从资产库挑（≤3 条），
  镜头存的是**素材 id**（库里 id 才是真相，名字只是显示用的别名）。
- **「登记公网直链」整条拆掉**：`POST /assets/url` 接口、对话里的 `add_asset`
  工具、`source="url"` 这一档，全部删除。素材只有「上传」一条入库通道。
- **提交给服务商前统一内联**（`app/media/inline.py`）：本地素材读出字节转成
  `data:...;base64`，公网直链原样透传。这是必须的——实测服务商只认
  `http(s)://` 或 `data:...;base64`，本机回放地址它拉不到（见 DEVELOPMENT 5.29）。
- **不合格的素材当场挡掉**：参考视频时长必须在 2–15 秒（服务商硬约束），
  在**保存提示词**时就量一遍并报明确原因，不让用户白跑一次生成。

**理由**：一个入口比两个入口干净，而且**用户要的能力没有少**——参考素材本来
就是「我导入的参考视频」，导入即用；之前那条公网直链只是被服务商的限制逼出来的
绕路，限制一旦用内联绕过去，这条路就没有存在必要了。

**什么时候该推翻**：如果出现「素材必须放在公网才有用」的真实场景（比如素材库要
跨机器共享、或单条素材大到内联不划算），再把「登记外部链接」作为一个**资产库
里的入库存档**加回来——但要加在资产库，不要加在提示词里。

**相关**：`app/media/inline.py`（内联）· `app/media/probe.py`（量时长/尺寸）·
`app/api/video.py`（`_auto_references` 合并参考素材与自动接力）·
`app/api/assets.py`（唯一入库通道：上传）· `docs/DEVELOPMENT.md` 5.29

<a id="d-38-出片幂等用数据库claim会话互斥用进程内锁"></a>
## D-38 出片幂等用数据库 claim，会话互斥用进程内锁 —— 已定（2026-11-10）

**背景**：D-36 的对标结论里，「生成授权闸门」是我们要补的最大洞：
`submit_videos` 是 Agent 可反复调用的工具，同镜头重复提交 = 重复扣真钱；
同一会话并发两轮 = 消息交错、摘要互写。两个都是「会咬人」的稳定性问题，
但它们的**生命周期完全不同**，所以用了两种锁。

**选项**（出片幂等）：① 提交前查一次「同镜头有无在途任务」；② 数据库 claim 表
（意图指纹占位，compare-and-swap）；③ 引一个任务队列中间件（Celery/Redis）。
**选项**（会话互斥）：① conversations 表加 `active_run_at` 列 + stale 超时 + 启动清零；
② 进程内 `threading` 锁表。

**决定**：出片用 ②，会话用 ②。

**理由（出片为什么是 claim 而不是简单查询）**：① 的「查了在途再决定」有一个
查不到的窗口——`create_video_job` 与投递队列之间进程死了，库里留下一条
永远 pending 的僵尸任务，① 会把后到的请求也挡死（它只认在途任务）。
claim 表把占位提到建任务**之前**：占到 claim → 建任务 → `finish_video_claim` 落定；
任务进终态时由 `update_video_job` 的钩子**一处收口**自动释放（队列回写 / 取消 /
巡检判失败 / 质检全部经过这一个函数，不用每个调用点记得释放）。
崩溃遗留的空 claim 由 10 分钟超时自愈。另有一层前置比对 `_same_intent`：
成片质检的自动重 roll 直建任务、不走 claim，所以 claim 未命中时还要查一次
「同镜头有无同意图的在途任务」兜底，否则「质检刚重 roll + 用户又说出片」
会让同一镜头两条任务并行烧钱。
③ 引队列中间件与「克隆下来就能跑」的单机定位冲突（D-07）。

**理由（会话为什么不是落库）**：对话 run **不跨请求存活**——一轮对话就活在这个请求
的线程里，进程重启它就没了，内存锁随进程自然清空，不需要 stale/启动清零这类
清理路径。落库方案的复杂度（心跳、超时、崩溃残留）是为「活得比请求久的资源」
准备的，对话不是这种资源。本产品是单进程本机服务（无鉴权、仅本机），
进程内锁覆盖全部并发来源；真到了多进程部署那天，再回来补落库版本。

**代价与边界**：claim 的 key 是 sha256(意图指纹)，**参数变了就是新意图**——
这是刻意的：换时长/画幅/参考素材再提交是合法的「重出片」，不该被挡。
等价归一化（空值=没提、显式默认值=没传）在 `video_claim_key` 一处定义。

**什么时候该推翻**：多进程部署（gunicorn workers > 1）时进程内锁立刻失效，
会话互斥必须换回落库方案；出片 claim 本来就是库里的，不受影响。

**相关**：`app/store.py`（`VideoJobClaim` / `claim_video_job` / 终态释放钩子）·
`app/api/video.py`（`submit_video_job` 唯一提交口）· `app/video/batch.py`
（`running_for_project` 批次互斥）· `app/chat/conductor.py`（`acquire_thread` 等原语）·
`app/api/chat.py`（409 与释放出口）· `tests/test_video_idempotency.py` ·

<a id="d-39-首页输入框是开新作品的起点不是独立模式"></a>
## D-39 首页输入框是「开新作品的起点」，不是独立模式 —— 已定（2026-11-10）

**背景**：首页大输入框发「帮我做成短剧：…」后毫无反应（实测：后端其实走通了，
Agent 建了作品，但前端停在首页；第二轮还 404）。当时存在两种理解：
「首页输入框是个轻量试玩，正式流程还得走新建作品」vs「首页输入框就是正式入口」。

**选项**：
① 首页发送先弹「新建作品」引导，用户填完才发；
② 首页发送 = 直接开聊，Agent 聊出作品时把这段对话**迁进**那部作品，
   前端发送即切进对话视图；
③ 首页只做展示，输入框挪走。

**决定**：**选 ②**。这是 D-24「对话优先」的必然推论：
- 用户已经在输入框里说出了需求，再拦一道「先建作品」表单就是流程倒退（①否）；
- 首页输入框是产品门面，挪走等于承认它没用（③否）。
- 落地三件：发送即 `mode='workspace'`（反馈）；本轮从全局线程建了作品 →
  整段对话迁进作品默认对话、done 回真实 conv id（归属 + 接续）；
  同轮后续工具的 project_id 兜底动态读 collector（不漏挂）。

**理由**：「把它聊出来」的那段对话**就是这部作品的来路**——第一稿怎么来的、
名字怎么定的，全在那段对话里。留在全局线程等于作品没有出生证明。

**什么时候该推翻**：如果以后支持「一个全局对话里聊出多部作品」，
整线程迁移的时机判据要收窄到「本轮消息」；届时按消息 id 集合迁，别按线程迁。

<a id="d-40-byok-的能力清单由厂商发现用户勾选而不是我们硬编码"></a>
## D-40 BYOK 的能力清单由厂商发现、用户勾选，而不是我们硬编码 —— 已定（2026-11-10）

**背景**：用户问「声音库这么少，这些声音是调模型生成的还是找的？」。真相是第三种——
我们硬编码了 8 个 MiniMax 音色 ID。但我们是 BYOK 产品（D-… 视频统一 MiniMax + 用户自带 key）：
key 是用户的，可用能力清单也是用户账号的属性，凭什么由我们在代码里写死 8 个？
实测 `POST /v1/get_voice` 一把 key 能问出 **303 个系统音色**；对话模型那边
「测试连接」早就在调 `/models`，只是把结果当一次性提示扔了。

**选项**：
① 继续硬编码，人工扩充到几十个；
② 拿用户的 key 去厂商发现全量 → 存库 → 用户勾选启用 → 下游只从勾选集取；
③ 不做勾选，发现多少全塞进下拉。

**决定**：**选 ②**，对音色与对话模型统一采用「发现 → 落库 → 勾选」这套机制。

- **音色**：`VoicePool` 表存发现的音色（全局，因为它是 key 的属性不是作品的属性），
  `POST /voices/discover` 拉厂商清单、`PUT /voices/pool` 存勾选；
  `build_voice_pool` = 勾选在前 + 内置 8 个兜底 + 克隆音色。
- **对话模型**：`/providers/{id}/test` 返回全量模型（去掉 `names[:12]` 截断），
  设置页「发现模型」按钮 → 勾选 → 并入现成的模型清单（复用 toggleModel/saveModels）。
- **视频模型是例外**：MiniMax `/v1/models` 不返回 `MiniMax-H3`，实时发现这条路断的，
  保持手填并在 UI 如实说明——不假装能发现。

**理由**：① 硬编码永远追不上厂商的清单，而且替用户做了他没要求的筛选；
③ 303 个直接铺进下拉等于没设计，用户还是不知道选哪个。
② 把「有什么」的真相交还给厂商，把「用哪些」的决定权交还给用户——这才是 BYOK。
**内置 8 个永远兜底**（空勾选 = 与改造前逐字节一致），所以这不是替换，是叠加。

**关键约束（实测决定设计）**：厂商不给音色性别，只能从 id 前缀推；
推不出的（287/303）归 other，**other 不参与自动选角**（猜性别出过事故，见 5.19），
只供人工指定。自动选角因此仍依赖「勾选出来的男/女池」。

**什么时候该推翻**：如果厂商补了带性别/年龄标签的音色接口，other 那批就能归位、
自动选角可用范围立刻扩大——那时该重新拉一次而不是继续用前缀猜。

<a id="d-41-配置权威从-env-翻转为-db-现有-key-幂等入库"></a>
## D-41 配置权威从 .env 翻转为 DB，现有 key 幂等入库 —— 已定（2026-11-10）

**背景**：用户要求「从现在开始都不走 env，把现有的 key 和数据都入库，走真实 BYOK」。
盘点时发现 env 一直在**悄悄覆盖 UI 选择**：设置里配的是 `deepseek-v4-pro`（DB 行），
实际跑的却是 `.env` 的 `deepseek-flash`——「设置 → 模型」形同虚设，
这与 D-40「BYOK 的能力清单归用户」的精神直接冲突：key 和选择都是用户的，界面必须说话算数。

**选项**：
① 彻底切断 .env：解析链无视 env，key 只能从 UI 进 DB；
② DB 权威 + env 降为空库兜底：DB 有配置以 DB 为准，空库时 env 仍能起跑；
③ 只加「UI 显式偏好」入口压 env（现状的延伸，env 链仍是主配置源）。

**决定**：选 ②，配一次性幂等种子（`app/llm/seed.py`）。

**理由**：
- ① 破坏「克隆下来就能跑」的硬指标（D-07），且空库时服务直接不可用、
  start.bat 首跑体验与全部 env-only 测试都要陪葬；
- ③ 已经试过——UI 偏好只覆盖 chat 一维，vision/image/tts 仍被 env 压着，
  而且偏好没设过时 env 照样赢，等于没修；
- ② 把「能跑」和「说话算数」分开解决：DB 是权威（四模态一致），
  env 只在 DB 空时兜底（新装/删库不裸奔）。

**种子的三条铁律**（用户数据，跑一百遍不许改坏）：
1. **只补缺不覆盖**——同 (kind, name) 已有带 key 的行就跳过（那是用户 UI 定的）；
2. **不设 model_preference**——单行时 DB 兜底自然选中，多行时由用户在 UI 选，
   种子设偏好反而可能把选择盖回 env 字面值；
3. **空 env 不动空库**——env 里没有对应 key 就什么都不做。
搬的是「当前实际生效的配置」（store=None 的 env 视图解析结果），不是 env 的字面默认值。

**副作用要如实告知**：翻转后 chat 从 flash 变成 UI 里配的 v4-pro——这不是 bug，
是用户选择终于生效了；想换回 flash 在设置里点一下即可（现在点了真的管用）。
备用 key 轮换（`app/keys.py`）继续读 os.environ——那是故障转移的安全网，不是配置入口。

**什么时候该推翻**：若出现「多机器共享一份 DB、各机 env 不同」的部署形态，
env 兜底语义会失效，届时配置应完全走 DB + 显式导入导出。

**相关**：`app/llm/registry.py`（四 resolver 的 DB 优先链）· `app/llm/seed.py` ·
`app/main.py` lifespan / `app/cli.py`（启动钩子）· `tests/test_byok_seed.py`（8 用例锁幂等三原则）·

<a id="d-42-内置厂商目录加一步流选厂商填key拉模型勾选"></a>
## D-42 内置厂商目录 + 一步流：选厂商 → 填 key → 拉模型 → 勾选 —— 已定（2026-11-11）

**背景**：用户提了三件事——① 「添加厂商」应叫「自定义供应商」；② 内置常见厂商

③ 「模型配置的前端做的还是不行」。根因是原设置页把「厂商」和「模型」两件事混在一个

用户得在两个界面来回——对内置厂商来说模型名本该由厂商自己报。

① 只改文案（添加厂商→自定义供应商），流程不动；

    发现成功一律以厂商实时清单为准（不替用户筛选，见 D-40 的"清单不截断"）；
  - 左列是「目录 ∪ 已配置」合并视图：内置厂商没配过显示"待配置"，配过显示真实行；
  - 「自定义供应商」表单去掉模型名/预设下拉，只留 名称/显示名/Base URL/Key，
    保存后引导点"发现模型"——中转站/自建网关也能接。

**内置目录**（`providers.py`，OpenAI 兼容的对话厂商）：DeepSeek、智谱 GLM、通义千问、

## D-43 提示词批准改为服务端硬闸门：模型只能发起，用户确认才生效 —— 已定（2026-11-11）

**背景**：全面体检发现「批准 → 出片」这条花钱链路的约束全是提示词级的——
`approve_video_prompts` 是普通工具，模型理论上可以同一轮自己批准、自己出片
（8 步工具预算完全够）；小说原文会进上下文，注入面真实存在；编造拦截只拦
「没调工具却声称做了」，不拦「越权调了工具」。同时 REST 侧出片闸门本身可绕过：
`submit_video_job` 的校验写成 `if shot and ...`，传一个不属于该作品/不存在的
version_id 或 shot_id 时 shot 解析为 None，整段闸门被跳过，任意未批准的
prompt 能直接付费出片。

**选项**：
① 维持提示词约束，只修 REST 绕过漏洞；
② 服务端硬闸门：工具只能「发起批准请求」（落 pending_approvals 表 + 对话确认卡片），
   真正写 approved 只有两条确定性路径——用户点卡片（meta.intent，浏览器发的）
   或用户下一条消息被保守的确定性检测命中（消息来自 API 请求体，模型伪造不了）；
③ 每次批准弹浏览器原生 confirm。

**决定**：选 ②，并同步把 REST 闸门改成 fail-closed。

**理由**：①的软约束在「模型可被原文注入」的前提下不成立；③打断对话流且
无法承载「批准哪些镜头」的信息。②复用改编审阅 resume 的确定性路径模式
（同一套 meta 机制），多一步交互换来「花钱动作必须有用户的服务端证据」。
fail-closed 闸门再加一道等值校验：提交的 prompt 必须与该镜头已批准的 prompt
逐字一致（所有合法调用方传的都是库里那条，只挡「换一条没批过的词硬塞」）。
`edit_shot_prompt` 编辑后状态重置 needs_review——编辑使批准失效，语义闭环。

**副作用与边界**：
- 确认检测（`detect_confirmation`）刻意保守：短消息（≤30 字）+ 含确认词 +
  无否定/疑问标记才算。宁可漏判（用户再点一次卡片）也不误判放行付费。
- 同会话新请求把旧 pending 置 expired：提示词又出新版本时，旧卡片不该再能批。
- UI 工作台的逐镜批准按钮不经闸门（点击本身就是用户意愿），保持原样。
- 历史回放时卡片状态从 DB 回填，刷新后不会挂着失效按钮。

**什么时候该推翻**：若将来引入鉴权/多用户，「用户发起」可以直接由会话身份
证明，确定性文本检测可退役，只留卡片路径。

**相关**：`app/chat/approvals.py`（apply_approval + detect_confirmation）·
`app/store.py`（PendingApproval 表）· `app/chat/conductor.py`

## D-50 提示词规则的落地形态：可机械检测的「必须有」一律代码兜底，不靠文本说教 —— 已定（2026-11-13）

**背景**：一天内三处实锤，模式完全一致——SKILL 教了规则，模型不执行，
产物系统性劣化，用户为劣化买单：
① 运镜：规则写「动作与运镜并重」，实测固定机位 11/14、正文明写
「camera locked off」（`enforce_motion_ratio` 闸门后 evals DIR-11 清零）；
② 台词：规则 9 教官方音画句式，重生成 21 镜正文台词 0 句（native 成片因此
没有台词人声；兜底=按 `dialogue_ref` 从剧本节拍机械回填）；
③ 成组：D-49 翻转默认值的文案改完重生成，24 镜仍只 2 格进组
（`auto_group_scene` 兜底后 25/25）。
同族旧案：时长预算（5.38「批评管不住的数，代码来管」）、批准硬闸门（D-43）。

**选项**：① 加密说教文本、或换更强模型再试；② 立规矩：凡「必须有」的提示词
特征一律配确定性检查 + 代码兜底，SKILL 只负责教「写得好」，不负责保「写没写」；
③ 全部规则硬编码化，弃用 LLM 自由写作。

**决定**：选 ②。准入判据一条：**漏写可机械检测**（正则/计数/求和）的规则
才进兜底清单；检测不了的（文笔、戏剧判断）留在批评回喂层。③ 会毁掉链路
创造力上限——我们在买模型的写作能力，只是不再信它的自觉。

**理由**：回喂批评的成本是整轮导演调用（钱+分钟），兜底的成本是几行代码；
批评对 deepseek 级模型的约束力一天内被三次证伪，格式遵循本就是它的已知
弱项（DEVELOPMENT 踩坑实录、记忆 [[deepseek-format-adherence]]），说教治不了弱项。

**什么时候该推翻**：主力模型换代后格式遵循显著变好，可逐个撤兜底——
撤的判据是 evals 对应规则连续两轮 critical=0，撤前跑对比。反向信号：
兜底本身系统性产生劣质产物（如无脑成组导致组内崩），收紧兜底触发条件，
而不是回退说教。

<a id="d-51-切镜语法统一时间戳"></a>
## D-51 组切镜语法全厂商统一为时间戳方言，删除 Seedance 分支 —— 已定（2026-11-14）

**背景**：5.37 文档口径「Seedance 2.0 不认精确时间戳，2.5 才认」，昨天据此
给折叠层加了 `镜头N（秒数）：` 分支。但「官方不支持」≠「写了无害」也
≠「分支语法更准」——三个假设都没测过，而分支每多一处就多一处接线坑
（同日审阅差点漏传 provider 参数）。花 ¥31.9 做三方言实验：同一 3 机位
14s 组在 Seedance 2.0 上各投一次两种方言 + 2.5 探针一发。

**选项**：① 保留 provider 分支（2.0 镜头N / MiniMax+2.5 时间戳）；
② 统一时间戳语法、删分支；③ 统一镜头N 语法（2.0 官方口径方言）。

**决定**：选 ②。【已被 D-52 取代——用户看片四维反馈（B 的语速/音准/运镜/
叙事节奏更好，C 音调不喜欢）+ 切点精度数据，构成本条预留的推翻条件；
且「同级误差」表述不诚实：-1.12s vs -0.29s 不同级】
**理由**：实测三证据——(a) 时间戳版画面**零文字渲染**（抽帧 2s/6s/12s 全
净，「写了有害」假设排除）；(b) 两种方言三机位照常执行，切点误差同级
（镜头N：3.75/9.71 vs 预算 4/10；时间戳：3.54/8.88——分支没换来精度，
第二刀反而早 1.1s）；(c) MiniMax 原生时间戳、2.5 官方支持、2.0 实测无害
——一条语法三厂商，`_apply`/`_fold` 的 provider 参数全删，接线面收窄。
③ 是「为 2.0 的未证实收益牺牲另两家的原生语法」，方向反了。

**什么时候该推翻**：出现实测「时间戳写法在某厂商把数字渲染进画面」或
「某厂商镜头N 语法切点显著更准」的成片证据时恢复分支；2.5 上量后若
官方文档给出切点精度承诺，按承诺复核。

<a id="d-52-切镜语法按厂商分支恢复"></a>
## D-52 切镜语法恢复按厂商分支：Seedance 用「镜头N（D秒）」，MiniMax/2.5 用时间戳 —— 已定（2026-11-14，取代 D-51）

**背景**：D-51 依据 n=1 实验删了分支（判据：画面无害+切点「同级」）。
用户看片后给出四维反馈：B（镜头N 方言）在**语言速度、角色音准、镜头运镜、
叙事节奏**四项全部更好，C（时间戳）「不差但语速和音调不喜欢」。复核
数据发现 D-51 的两处失误：①「同级误差」不诚实——B 切点 -0.25/-0.29s，
C 第二刀 -1.12s，差一个量级；② 机器只测了画面文字与切点，**语速/音调
是未测维度**，恰是用户偏好的主因——机制可信：`镜头N（D秒）` 给每机位
显式报时长，模型把台词与表演往窗口里装，语速被秒数锚住；时间戳只给
绝对切点，台词长度无人认领。

**选项**：① 维持统一时间戳（D-51）；② 恢复 D-51 前的分支（Seedance→
镜头N，其余→时间戳）；③ 全厂商统一镜头N 语法。

**决定**：选 ②。
**理由**：推翻条件正是 D-51 自己预留的（「镜头N 在某厂商显著更优的
成片证据」），现在兑现了——主观四维 + 客观切点同向，n=1 但两种测量
独立、方向一致，且机制可解释。③ 不选：MiniMax H3 官方增强提示词
原生时间戳语法，三源调研背书过，无理由让表现未验证的写法替换原生写法；
2.5 官方文档也认时间戳。① 不选：等于无视用户验收标准（语速/音调
是成片质量的直接构成，不是边缘偏好）。
**教训**：D-51 的错误不是「做了实验」而是「用部分指标给全指标结论」——
删分支前应先问「观感维度测了吗」；机器可测的（文字渲染/切点）与
不可测的（语速/音调/节奏）要分开声明，不可测部分交给人，而不是用
可测部分替它签字。

**什么时候该推翻**：Seedance 2.5 实测「镜头N」语法切点同样准且语速同样
好时，可合并 seedance 全系走镜头N；或 MiniMax 出现镜头N 语法更优的
成片证据时重议统一。

**相关**：`app/crew/dp.py`（`_fold_group_prompts` provider 分支恢复）·
D-51（被本决策取代）· `~/.wenju/runs/ab_dialect_1114/ab_B_镜头N方言.mp4`
（用户验收基准片）· DEVELOPMENT 5.37
